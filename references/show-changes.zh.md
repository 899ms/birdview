# 阶段 2：表达变更

[English](show-changes.md)

输入：可用架构地图和用户授权的编码任务。
输出：符合 `schemas/activity.schema.json` 的有序 JSONL 事件。
状态转换与交叉引用规则见 [contract.zh.md](contract.zh.md)。

阶段 1 是前提。使用其选定并检查过的项目地图，包括准确的 `project.id`、`mapId`、`revision` 和现有模块 ID。若尚未建立可用地图，先回到 [map-project.zh.md](map-project.zh.md) 的发现与复用步骤，再生成活动。不要替换成虚构示例，也不要仅从文字推断目标 ID。地图覆盖缺失或过时应在阶段 1 解决；确实未归属的文件按下述规则明确记录。

1. 编辑前追加 `planned`：整体 `scope`、当前 `targets`、相对项目的文件路径，以及用模块职责表达的简短原因。
2. 每组编辑前追加 `editing`，保留完整范围，将目标缩小到当前编辑的模块，并列出具体路径。
3. 运行检查前追加 `verifying`。验证文件可能是测试或测试数据路径，不自动视为已修改文件。
4. 任务结束时追加 `completed`、`failed` 或 `cancelled`。适用时在 `checks` 中记录真实命令、退出码和观察结果。

本版本所有事件都是 `agent-declared`；事件名称不是自动文件系统观测。检查实际运行前，验证状态保持待定。不能因为事件成功写入就把任务标为成功。

每个事件携带完整范围与目标，消费者不需要从文字推断。范围需要扩大时，先发出另一个 `planned` 解释变化，再编辑新增模块。`editing` 不能悄悄扩大声明范围。

归属地图中不存在的文件仍留在 `files`，并且必须出现在 `unmappedFiles`。不要为了通过校验编造模块归属。修改有归属的文件时，目标应包含所有匹配的所有者；若归属规则过宽或重叠会误述系统，应在阶段 1 改进规则。

v0.1 每个会话只允许一个活动任务。终态事件后使用新任务 ID。会话序号单调递增，会话内不复用任务 ID。一个会话始终使用相同项目 ID 和地图修订版本。新地图版本使用新会话和事件文件。

## 预览边界

发布记录后，渲染选定地图及其活动文件：

```sh
node <skill-root>/scripts/render.mjs <map.json> <activity.html> <activity.jsonl>
```

渲染器写入 HTML 前校验整条事件流。版本不匹配、非法转换和文件归属不一致都会失败，且不会替换旧输出。仅在渲染成功后交付或打开新 HTML。
真实活动从最新记录开始，模拟活动从第一条计划开始。页面提供架构、更改和对照模式、历史选择及可折叠的文件与检查详情。对照使用相同模块位置，选择、缩放和滚动联动；窄屏上下排列。编辑前即高亮计划目标，范围使用轮廓，非目标模块弱化。验证目标与编辑目标分别标识。
阶段、文件和检查描述当前记录，不是累计 Git 差异。终态记录移除当前目标光晕；没有执行检查的完成记录必须明确保持未验证。

`--simulation` 仅用于虚构记录，例如 `examples/harness.activity.jsonl`；不要将其标成观测到的修改。
活动文本优先使用事件的 `translations[locale].reason` 和检查的 `translations[locale].summary`，缺失时回退原文。双语活动视图应为每种支持语言提供这些翻译。

这是文件快照：新记录需要重新生成并刷新。尚无浏览器文件上传、自动刷新、实时拦截或 Git 验证。未来显示回执只确认渲染，不代表批准或正确性。
