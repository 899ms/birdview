# 阶段 1：建立项目地图

[English](map-project.md)

## 输入与输出

输入：项目根目录、用户期望范围，以及可能存在的地图。
输出：符合 `schemas/architecture.schema.json` 的 `architecture.json`，以及从同一数据渲染的独立 `architecture.html`。
`examples/architecture.json` 仅用于参考字段结构，其系统是虚构的。
阅读 [bilingual.zh.md](bilingual.zh.md)：默认使用触发请求的语言，遵循明确的输出语言要求，不询问语言选择。仅双语交付使用严格双语校验。复用现有架构数据和翻译，必要时添加交付语言，不要重新构建。

## 创建前先发现

先检查用户提供或项目指引引用的架构路径，再检查项目现有产物位置，包括 `.birdview/`、根目录与 `docs/` 中的架构文件。限定文件名搜索 architecture/map 的 JSON、HTML、Markdown 或 Mermaid 产物，排除依赖、生成输出和技能示例。只有这些位置和项目引用没有结果时才扩大搜索。

阅读候选内容；文件名匹配不证明地图可用。确认它描述当前项目并覆盖相关职责。接受地图前，必须与下述应用清单核对覆盖范围；找到现有地图不能代替范围检查。对 Birdview JSON 运行校验，并核对相关范围内当前文件的归属和源码证据。Schema 有效不证明数据最新。优先使用用户选择或项目文档指定的权威地图，仅在证据无法解决候选冲突时询问。

在原位置复用兼容数据。如果现有图使用其他格式，将其作为证据，在检查源码后导出 Birdview JSON，保留有意义的标识和原产物。若只有 HTML 或图片，阶段 2 前先建立底层模块与归属数据。更新过时部分，不要默认重新生成整张地图。只有没有可复用或调整的地图时才新建。无法运行校验时报告限制，并在阶段 2 前解决。

按下述步骤渲染并交付选定地图，随 HTML 报告路径、`project.id`、`mapId`、`revision`、覆盖范围和不确定项。未提供编码任务时，完成可视化架构结果后停止并询问预期修改；不要把重新建图与变更跟踪当成可互换的下一步。

## 明确范围与应用覆盖

归纳模块前，明确用户需要整个仓库还是指定子系统。遵循明确范围；未限定的项目架构请求使用选定项目根目录，不能只看首先发现的构建系统。不要把仅后端任务扩展成无关应用审计。

在范围内阅读根 README、顶层目录名和相关工作区/构建清单，沿声明的成员和应用路径检查。搜索应有边界，排除依赖和生成输出。例如 Maven `pom.xml` 描述 Java 模块，也要检查根 `package.json` workspaces、`pnpm-workspace.yaml` 或文档中的 `apps/` 是否声明独立 Web 应用。这些只是发现线索，不是必需技术。

对每个候选应用，通过自身清单、启动/构建入口和相关源码确认职责：前端看浏览器挂载和路由，API 看服务启动，worker 看任务入口。只有 React 依赖不能证明存在前端应用。声明客户端与服务端连接前，追踪调用和路由。职责独立的用户端/管理端应用应保持可见，共享包不一定算应用。不要编造源码证据不支持的前端或其他类别。

新地图与复用地图都要核对应用清单。范围内每个应用必须对应模块、得到解释的分组，或明确的待解决覆盖缺口。补齐已验证遗漏时保留现有 ID，遵循修订规则。不要为了 6–10 个节点目标删掉应用。普通局部编辑只复查相关入口与变化的清单；范围或工作区结构改变时才重新广泛发现。

交付时在架构表旁简述已检查根目录和范围、应用及对应模块 ID、排除项和未解决区域，不需要新增 JSON 字段。零不确定模块只表示已展示模块没有记录不确定性，不证明仓库完整覆盖。区分“未检查”和“已检查但未发现应用”。

## 建立或完善地图

对缺失或过时覆盖，从 README、应用入口和相关包配置开始，沿主要请求或数据路径追踪核心模块。分配职责前阅读符号上下文，不能只看文件夹名称。当请求范围可被连贯描述时停止；不要枚举每个文件，也不要凭局部检查声称覆盖全仓库。

首屏争取约 6–10 个有意义模块，这是可读性目标，不要求编造或遗漏模块。使用项目术语命名职责。外部服务解释真实关系时纳入地图，但不给它们分配本地文件归属。

每个本地模块记录：

- `id`：独立于展示名称的稳定标识。
- `responsibility`：拥有的职责，不是文件名清单。
- `role`：根据检查的职责选择 `frontend`、`backend`、`cache`、`database`、`queue`、`security` 或 `generic`。它控制统一图标和配色，不可为了视觉多样性轮换角色。不明确时用 `generic`，角色独立于本地/外部归属和分组关系。
- `ownership`：精确文件与目录前缀，分别填写 `kind`。
- `evidence`：路径、可选符号/行号范围，以及它们支持什么结论。
- `status`：检查证据支持描述时用 `supported`，否则用 `uncertain` 并给出具体 `openQuestions`。
- `layout`：非负行列提示，用于稳定网格渲染。

记录有向关系并给出具体标签，例如“加载商品”。每条关系都要有证据和状态。`supported` 表示作者检查过支持代码，不是 Birdview 静态证明了关系。每条关系填写 `kind`（`request`、`result`、`dependency`、`event`、`control`）及 `visibility`（`overview` 或 `detail`），定义见契约。
核心执行路径、必要的结果/工具反馈、基础依赖和必需审批步骤放在 `overview`；恢复、重试和诊断可以放在 `detail`，除非它们就是地图主题。不要为了数量或缩短路径隐藏边，不明确时选择 `overview`。检查孤立概览模块是否遗漏基础连接；保留真正的辅助模块及其隐藏关系计数。所有关系都保留在数据中。关系类型与可见性都不代表 AI 修改范围。

展示包含模块、职责、归属、证据和不确定性的架构表，以及简短关系列表；两者都来自同一 JSON。允许用户纠正模型，但已有指令授权继续时，不要再强制多余审批。

## 复用与更新

可选 `groups` 表示明确的系统/子系统成员关系。每组包含 `id`、`name`、唯一 `members`（模块 ID）和非空源码 `evidence`。仅使用一层且成员不重叠，不从本地/外部代码归属推断系统边界。查看器并排排列分组，保留组内行列顺序；未分组模块在外框之外。没有成员关系证据时省略分组。组名和证据说明采用与模块相同的翻译约定。

创建分组时，根据源码证据支持的职责填写 `role`。共享模板为每类指定固定色系：

| 分组角色 | 含义 | 色系 |
| --- | --- | --- |
| `interaction` | 用户交互与审阅 | 淡蓝 |
| `runtime` | 执行与调度 | 淡暖黄 |
| `external-services` | 所描述系统之外的集成 | 淡紫 |
| `generic` | 未指定或混合职责 | 中性灰 |

证据不能确定类别时使用 `generic`；未填写也按 `generic` 渲染。不要根据分组顺序、名称、模块归属或颜色多样性选择角色。在分组证据说明中解释分类。分组角色独立于模块角色、部署或信任边界，以及计划/当前活动状态。

映射保留在共享模板内：不要往地图数据添加自定义颜色字段，也不要为单张地图覆盖模板调色板。Schema 拒绝未知角色和字段，但不能验证分类真实性；交付前检查引用证据。复用时保留现有角色，除非新证据支持变化，并遵循下述版本规则。

任务产物存入约定的项目位置，默认 `.birdview/`，不覆盖无关文件。替换现有地图前先阅读。`project.id` 和 `mapId` 是作者定义的本地标识，不必是公开 URL。`project.revision` 可选记录 Git 提交，不是地图修订版本，也不证明工作区干净。

保存地图的任何变化（包括布局）都增加 `revision`。职责持续存在时保留 ID，不将已移除的 ID 复用于其他角色。在旧地图上完成或取消任务后，才针对新版本开启任务；不要静默把旧事件重放到新地图上。

## 渲染与交付

建立或更新 JSON 后运行自带渲染器。工作目录为用户项目时使用绝对路径。`<skill-root>` 是包含 SKILL.md 的目录，不是用户项目根目录：

```sh
node <skill-root>/scripts/render.mjs <project-root>/.birdview/architecture.json <project-root>/.birdview/architecture.html
```

复用其他位置的 JSON 时使用真实路径。HTML 存入约定产物位置，避免替换无关文件。渲染器校验地图后写出自包含 HTML，不需要服务端或网络资源。不要手写另一套查看器，也不要用虚构聚光灯演示替代真实项目架构。

在可见浏览器预览中打开 HTML，不是编辑器文件标签。在 Codex 中若有 `open_in_codex`，使用 browser 目标与正确编码的文件 URL，例如：
`{ "target": { "type": "browser", "url": "file:///D:/Project/.birdview/architecture.html" } }`。
主要可视化交付不能用 file 目标。Markdown 文件链接可能打开源码编辑器，仅给链接不能证明用户看到了图。

使用可用浏览器检查模块名称、关系和选中模块证据是否正确渲染。排队中的打开请求只证明请求已发出，不证明可见渲染；独立无头检查验证的是产物，不是用户可见浏览器标签。准确报告这些结果，不要都称为“已显示”。

### 交付前检查可读性

模板根据跨越网格轨道的关系估算拥挤程度，并选择间距和路径。不要在地图数据中重复像素阈值，也不要编造拥挤度字段。Agent 仍负责检查结果：自动间距不保证连接可读。

在用户可用视口中查看最终 HTML。检查概览与全部关系，再悬浮直接关系最多的模块（入边出边都算，自环算一次）。发现拥挤时检查其他区域。同时检查模块名称、证据详情与几何布局，特别是：

- 线条穿过卡片、沿通道重叠，或在转角聚集，导致端点与箭头方向无法区分。
- 路径或标题裁切、隐藏关系计数与视图不一致、适配全图后文字过小。
- 悬浮后直接关系是否可追踪，离开后是否恢复所选视图且节点不移动。

必要时按职责与交互顺序调整 `layout`，或仅在源码证据支持成员关系时完善分组。保留标识、归属、关系语义和完整范围覆盖。不要仅为清理拥挤区域而删除真实关系或修改 `visibility`。按版本规则更新，重新渲染并检查受影响区域与全图。地图未变化时，普通局部任务不需要无关 UI 审计。如果连续两次布局尝试都没有可见改善，停止调整并报告剩余可读性问题，不要反复重排。

报告实际检查的产物路径、视口、模式、重点模块和未解决问题。Schema 检查成功、碰撞抽样或成功截图本身都不等于视觉验收。当前没有内置自动视觉诊断，不要声称自动拥挤检查通过。浏览器检查不可用时标记未做视觉审查，并采用下述回退方式，不要声称已验证可读性。

浏览器访问不可用或被拒绝时，报告真实工具限制，提供明确标为 HTML 文件的绝对路径。解释浏览器打开会显示图，编辑器打开会显示源码。不要换机制绕过拒绝；没有渲染错误证据时，不要归咎模板。

交付先说明浏览器预览结果和 HTML 产物，JSON 是支持数据。渲染失败时修复错误或明确报告阻塞；只有 JSON 的结果不能称为完成可视化架构。

此视图是架构快照，不显示实时编码活动。
